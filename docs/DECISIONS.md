# Decisions log

Chronological record of non-obvious technical choices. Add an entry whenever a choice isn't
forced by the spec in CLAUDE.md / docs/*.

## Phase 0 — Repo & tooling

**Monorepo tool: pnpm workspaces.**
`pnpm-workspace.yaml` at root lists `apps/*` and `packages/*`. Chosen over npm workspaces for
faster installs and stricter node_modules (catches phantom dependencies). No Turborepo/Nx yet —
three apps don't need a build-graph tool; add one later if `pnpm -r build` gets slow.

**Package names: `@shaddai/api`, `@shaddai/customer`, `@shaddai/admin`, `@shaddai/ui`.**
Nest CLI and create-next-app both default to unscoped names (`api`, `customer`, `admin`); renamed
to a shared scope so `pnpm --filter @shaddai/x` is unambiguous and matches `@shaddai/ui`.

**Dev ports: api `3000`, customer `3001`, admin `3002`.**
create-next-app defaults both Next apps to 3000, which collides with Nest's default. Ports are
pinned in each app's `dev`/`start` script rather than left to `next dev`'s auto-increment, so the
port is predictable in docs/scripts/`.env` files.

**ESLint: kept each app's generated flat config, not a hand-unified one.**
Nest CLI generates `typescript-eslint` + `eslint-plugin-prettier`; create-next-app generates
`eslint-config-next` (which bundles its own TS rules). Both are already strict and idiomatic for
their framework; forcing a single shared flat config across Nest and Next App Router fights both
tools for no real benefit at this stage. What *is* shared: a single root `.prettierrc.json` —
removed the per-app `.prettierrc` Nest generated so there's one source of truth for formatting.

**Tailwind v4, CSS-first theme (not `tailwind.config.ts`).**
create-next-app scaffolded Tailwind v4, which configures via CSS `@theme` rather than a JS config
file. DESIGN-SYSTEM.md §7 shows a v3-style `theme.extend` object — translated 1:1 into
`packages/ui/src/theme.css` (see below) using v4 `@theme` syntax. Same tokens, different syntax.

**Shared design tokens: `packages/ui/src/theme.css`, imported via `@import "@shaddai/ui/theme.css"`.**
Both apps' `globals.css` do `@import "tailwindcss"; @import "@shaddai/ui/theme.css";`. Works
because pnpm workspaces symlink `@shaddai/ui` into each app's `node_modules`, and Tailwind v4
resolves `@import` through normal Node resolution. Each app's `next.config.ts` sets
`transpilePackages: ['@shaddai/ui']` so Next compiles the shared package's TSX instead of treating
it as pre-built.

**Fonts: `next/font/google`, not `next/font/local` — TEMPORARY, needs revisiting.**
DESIGN-SYSTEM.md §3 specifies self-hosting via `next/font/local` with vendored font files
(Space Grotesk, Inter, JetBrains Mono). No font binaries are checked into the repo. Using
`next/font/google` in `packages/ui/src/fonts.ts` instead: still build-time self-hosted with zero
runtime requests to Google, so it satisfies the *behavioral* requirement, but it's not what the
doc says to do. **Follow-up:** source the actual font files (open licenses — OFL) and swap
`fonts.ts` to `localFont()`, keeping the same `variable` names (`--font-space-grotesk`,
`--font-inter`, `--font-jetbrains`) so `theme.css` doesn't need to change.

**`packages/ui` exports both CSS tokens and React components.**
`Badge`, `SignalMeter`, `PlanCard`, `Ticket` are functional stubs (not empty placeholders) per
DESIGN-SYSTEM.md §5, exported from `src/index.ts` alongside the font instances. `Ticket`'s QR is a
`qrSlot` ReactNode prop, not baked in — the `qrcode` lib integration is Phase 3 scope.

**Nest API: global prefix `/api`, health check at `GET /api/health`.**
Matches the "API prefix `/api`" convention in CLAUDE.md. `AppController`'s default `getHello()`
was replaced with `getHealth()` returning `{ status: 'ok' }` (was Hello World boilerplate).

**Dev DB access: not yet decided.**
Phase 0 has no DB code (no ORM entities yet — that's Phase 1). SSH tunnel vs. local MariaDB
decision deferred to the start of Phase 1, when there's actually something to connect to.

## Phase 1 — API core: plans & voucher engine

**Dev DB access: SSH tunnel over Tailscale, against the real live DB — not a local copy.**
`ssh -L 3306:127.0.0.1:3306 server@<tailscale-ip>` forwards the server's MariaDB to
`localhost:3306`. Chosen over a local Docker MariaDB so schema drift is impossible — Phase 1
develops directly against the actual `radius` DB the whole system already runs on.

**ORM: Prisma, schema introspected via `prisma db pull` — never hand-written.**
`apps/api/prisma/schema.prisma` was generated by pointing at the live DB, not authored from the
CLAUDE.md table descriptions. This is the whole reason Prisma won over TypeORM here: the DB is
the source of truth, and `db pull` guarantees the schema file matches it exactly (no destructive
migrations risk, since Prisma migrations are never used against this DB — it's introspect-only).
Model/field names were renamed to idiomatic PascalCase/camelCase via `@@map`/`@map` after the
first pull; **confirmed** re-running `prisma db pull` preserves those renames (Prisma calls this
"schema enrichment" from the previous file), so re-introspecting after a live schema change is
safe and won't need the renames redone.

**Prisma pinned to 6.x, not the 7.x that installs by default.**
Prisma 7 hard-requires Node 20.19+/22.12+/24.0+ and refuses to install on Node 23.3.0 (an odd,
non-LTS release) — which is what's on this dev machine. Downgrading to Prisma 6.16 avoided
touching the system Node install. Revisit once the dev machine is on an LTS Node.

**`prisma`/`@prisma/client`/`@prisma/engines` added to `onlyBuiltDependencies` in
`pnpm-workspace.yaml`.** pnpm blocks postinstall scripts by default (supply-chain safety); these
three need theirs to fetch/generate the query engine, so they're explicitly allow-listed rather
than approved ad hoc per machine.

**`VouchersService.issue()` splits into `issue()` + `issueInTx(tx, ...)`.**
Prisma's interactive transactions (`$transaction(async (tx) => ...)`) each hold a dedicated
connection. Calling `issue()` (which opens its own `$transaction`) from *inside* another
transaction would silently run on a second connection — not atomic with the caller's writes. The
Paystack webhook (Phase 2) needs "mark payment success" and "issue voucher" to commit or roll
back together, so `issueInTx` takes an externally-supplied `tx` and `issue()` is just
`$transaction(tx => issueInTx(tx, ...))` for callers that don't need to compose it.

**RADIUS `Expiration` dates are formatted in UTC, not the API host's local time.**
Found by comparing `SELECT NOW(), @@system_time_zone` on the live DB (`system_time_zone = UTC`)
against the dev machine's clock (Africa/Lagos, UTC+1) — a one-hour mismatch. Initial
implementation used `date.getHours()` etc. (local time), which would have written expiry values
one hour ahead of what FreeRADIUS (same host as MariaDB, per CLAUDE.md) actually evaluates
against. Fixed to `getUTCHours()` etc. in `radius-date.util.ts`. Verified end-to-end against the
live DB: issued a monthly voucher, extended it, and confirmed the `radcheck` `Expiration` value
matches `vouchers.expires_at` to the second.

**Admin auth: single admin user via plaintext env-var comparison, JWT signed with `JWT_SECRET`.**
`ADMIN_EMAIL`/`ADMIN_PASSWORD` are compared directly (no bcrypt hash) — matches TODO.md's "single
admin user via env for now" scope. Fine for local dev/pre-launch; revisit before real admin
credentials go in (Phase 7 hardening is the natural point, or sooner if admin access moves off
your own machine).

**Voucher `extend()` only implemented for monthly plans.**
CLAUDE.md's core-invariant bullets only describe `Expiration` (monthly) and `Session-Timeout`
(hourly) as the two expiry mechanisms; extending an hourly voucher's duration isn't specified
anywhere and there's no obvious single right answer (extend the per-session cap? add a calendar
window on top of it?). Left unimplemented rather than guessed — `extend()` throws
`BadRequestException` for hourly plans until this is actually asked for.

## Phase 2 — Paystack

**Paystack TEST keys are live in `apps/api/.env` / `apps/customer/.env`, provided directly by you
in chat.** Both files are gitignored; verified via `git status` that they were never staged. One
close call: the keys briefly landed in the *tracked* `apps/api/.env.example` (probably a copy-paste
into the wrong file) and were caught via the `.env.example` diff before any commit — worth
double-checking `git diff --cached` on `.env.example` specifically after editing env files
side-by-side.

**Idempotency via a conditional `updateMany` claim, not a lock or queue.**
`processSuccessfulPayment` does
`tx.payment.updateMany({ where: { paystackReference, status: 'pending' }, data: { status: 'success', ... } })`
inside a transaction and checks `count === 1` before issuing a voucher. Two triggers can race
legitimately here — Paystack retries the webhook, and the customer status-poll endpoint
independently calls Paystack's verify API as a fallback if a payment is still `pending` — and
this makes only one of them ever proceed past the claim. Verified by replaying the same signed
webhook payload twice: second call returned the same voucher code, no duplicate voucher or
payment row.

**Status-poll endpoint (`GET /api/payments/:reference/status`) actively re-verifies with Paystack
if still pending, instead of only trusting the webhook.** No job queue exists yet to retry a
missed/delayed webhook, so the customer success-page poll doubles as a fallback delivery path —
it calls `paystack.verifyTransaction()` and runs the same idempotent `processSuccessfulPayment`
if Paystack reports success. Revisit if a queue gets added later (Phase 6+); this fallback can
likely stay either way as defense-in-depth.

**Webhook route reads `req.rawBody` via Nest's built-in `rawBody: true`, not a manually
disabled body parser.** `NestFactory.create(AppModule, { rawBody: true })` in `main.ts` makes
Nest stash the raw `Buffer` on `req.rawBody` for every request while still parsing `req.body`
normally — simpler than TODO.md's suggested "disable default JSON parse on this route" and
requires no route-specific middleware.
